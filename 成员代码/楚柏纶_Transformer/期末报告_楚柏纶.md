## 一、需求理解

本次工作围绕 Transformer 项目的推理入口展开。`forward()` 和 `generate()` 都会接收外部传入的 token 序列，如果不做边界检查，异常输入会直接进入 embedding 索引和注意力计算。本次修改主要处理 token id 校验、输入长度限制和生成长度限制。

## 二、风险识别

原始 `model.py` 中，`forward()` 直接执行：

```python
x = self.embeddings[input_ids]
```

这里至少有两个容易出问题的地方。第一，负数 token 在 Python 和 NumPy 里可能被当作反向索引，不一定会报错。第二，超长输入会直接进入模型计算，注意力计算对序列长度比较敏感，输入长度越大，资源消耗越明显。

本次识别出的主要风险是：

- token id 未校验，可能出现负数下标、越界下标或非整数输入。
- 输入长度和生成长度没有限制，可能造成不必要的计算资源消耗。

更完整的风险分析写在 `docs/risk-analysis.md`。

## 三、安全约束如何进入 AI 交互

在写代码前，我把风险整理成了结构化 Prompt。重点约束如下：

- `forward()` 必须在索引 embedding 前校验输入。
- `generate()` 必须在循环生成前校验初始输入和生成长度。
- token id 必须是整数，不能接受字符串、浮点数或布尔值。
- token id 必须满足 `0 <= token_id < vocab_size`。
- 输入长度和生成后的总长度都不能超过 `max_position_embeddings`。
- 异常输入统一抛出 `InputValidationError`。
- 校验逻辑必须进入实际代码路径，不能只写在注释里。

完整 Prompt 记录放在 `docs/prompt-records.md`，约束文档放在 `docs/constraint-doc.md`。

## 四、关键代码片段

新增的输入校验模块位于 `security_input.py`。

```python
class InputValidationError(ValueError):
    """Raised when model input violates the inference safety policy."""
```

这让异常输入有一个统一类型，而不是把 NumPy 的底层异常直接暴露给调用方。

```python
if token_id < 0 or token_id >= vocab_size:
    raise InputValidationError(
        f"input_ids[{index}] is outside the valid token range"
    )
```

这段代码明确拒绝负数 token 和超出词表范围的 token。负数 token 是本次审查中特别关注的点，因为它可能不会立刻报错。

`model.py` 中，`forward()` 现在会先校验再索引 embedding：

```python
input_ids = validate_input_ids(
    input_ids,
    self.config.vocab_size,
    self.config.max_position_embeddings,
)
x = self.embeddings[input_ids]
```

`generate()` 也会检查生成长度：

```python
max_new_tokens = validate_max_new_tokens(
    max_new_tokens,
    self.config.max_position_embeddings,
    len(ids),
)
```

## 五、审查发现的问题与处置

审查时发现原实现把输入合法性完全交给了 NumPy。这个写法在演示模型时很常见，但安全边界不够清楚。

处置方式是把校验前移到模型入口。`forward()` 和 `generate()` 都先调用 `security_input.py` 中的函数，只有通过校验后才继续执行矩阵计算。

我还补了测试，专门覆盖负数 token、越界 token、非整数 token、空输入、超长输入和生成长度过大这些情况，用来确认原问题确实被拦住了。
